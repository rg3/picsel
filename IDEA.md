i'd like to create a gui app to help me select pictures to keep and pictures to discard. when i go to an event, i take pictures with both my dslr camera and my phone. when i get home, i want to store all pictures together in the same directory as a gallery, but i like to discard bad pictures or similar ones, and my current workflow is a bit too slow, so my goal with the app is to streamline this selection process.

the usual setup is that i dump all pictures into a directory, then select which ones i want to keep and move those to a final directory. usually, the final directory is the parent of the all-pictures directory. for example, let's say i have a directory called 2026-11-21-Whatever and inside it i have a directory called "pending-selection". i then select which pictures from that subdir should end up in the parent directory containing the gallery and, once i'm done, i remove the pending-selection dir.

the app needs to work primarily with jpeg pictures, but maybe i can throw in some videos too, usually in mp4 format (likely h.264 and aac?). maybe in the future it has to suppport other picture formats or video formats. the app will be used on this computer, so the primary target platform is linux. it's going to run under my kde session but maybe in the future it would run under gnome, no idea. i don't want to select a specific toolkit to work with, or even if it should be a plain opengl app, or use browser-based technologies. that's your choice.

the workflow i imagine with this is like this: the app is registred in the system as valid to handle jpeg files, so when i right-click on the jpeg file in the file manager, i have the option to open the pic with the app. opening the file with the app, though, does not just open that file. the app takes that action as an intent to select the pictures in the directory that contains it. if it's the first time that i'm working with that directory it will present a dialogue to select a couple of things:

- which is the final dir for the selected pictures, and it should be the parent dir by default if it's writable for the user.
- if the pictures should be selected or deselected by default.

once that's set up, it will open the main window. i imagine the main app window as a large window with a panel on the left and a mosaic (matrix) of picture thumbnails on the right.

the thumbnails on the right, though, should be large so that, if possible, i can do the selection without actually needing to open the picture in its full size. perhaps 3 or 4 columns at most. each slot in the mosaic would be ideally sized in 3:2 proportions, which is the usual dslr proportion. phone pictures in 16:9 would be vertically centered in the slot, and vertical pictures in any aspect (9:16, 2:3, 3:4, etc) would be horizontally centered in the slot. should the pictures be right next to each other or should there be some margin or whitespace between them? undecided. what is clear is that each picture should show its current selection state clearly. i was thinking about a green frame around the selected ones and a red frame around the ones that are not, but this is just a suggestion. in the mosaic, we're working with a picture at any given moment. let's call this the "highlighted" picture so as not to confuse it with the picture selection process. the highlighted pic should be emphasized somehow. i was thinking about "zooming in" a bit on it, in the sense of making it slightly bigger, so it invades a bit the space of nearby pictures even. you can change the selection state of each picture by pressing a single-key on the keyboard, like "s" to select the picture for the final dir and "d" to deselect it so it won't be moved. typically, after doing one of those, the app moves to the next picture. we can also freely move between the pictures using the arrow keys. it should work similar to a text editor with a long line of text, i.e. i can press up or down to move between rows and, when pressing right in the last picture of a row, it should move to the first picture of the next row down. pressing left on the first picture of a row moves to the last picture of the previous row.

the panel on the left provides some info and an alternative interface to do actions with the mouse. for example, it could show the current target dir for the selected pictures and allow you to change it, the default action for new pictures (select or deselect) and allow you to change it, and some info about the current pic (e.g. file name, size, dimensions, some exif info maybe) and a couple of buttons to select or deselect the picture instead of using the keyboard shortcuts. it should be possible to change the highlighted picture also by clicking on the thumbnail with the left mouse button. the panel could also contain a short list of keyboard shortcuts in case i forget the keys.

once i'm fine with the current selection of pictures, a final action has to be triggered. typically only through an important button somewhere in the left panel that applies the "sieve": move the selected pictures to the final dir. it should have a confirmation dialogue just in case it's pressed by accident. likely it cannot be triggered by a keyboard shortcut, but i'm not sure. the confirmation dialogue would say "Move X pictures out of Y pictures to D?" with X being the number of selected pictures, Y the total number of pictures and D the destination directory, and "no" should be selected by default. once i confirm, the app proceeds to move the currently selected pictures to the final destination dir. the move should be as fast as possible. there may or may not be a progress dialogue. if the destination dir is in the same filesystem, the move can be done by creating a new hard link to the pic in the destination dir and  then removing the link from the source dir. this is instantaneous. if not, an actual copy may have to be made.

the selection state should be saved at all times. if the app crashes or i want to close it, it should be able to continue later where it left off. for this, i was thinking of a suggested mechanism: an sqlite database with a known name in the picture dir. the database can contain a config table with a key and a value columsn, both strings, where we can save the source dir (the same as the one containing the database), the final dir (absolute paths in both cases), the default action for new files (select/deselect), an app id and version number of the config file (stored as a string) as a backwards compatibility mechanism. a second table can contain file names in one column and the selection state (0 or 1) in the second column. when i choose to select or deselect a picture, the database is updated immediately with a transaction and saved. does this make sense?

the app should ignore anything in the source pictures dir that is not a regular file. i.e. it does not have to care about subdirs, for example.

the app should monitor the source dir for file deletions, additions and renames to update the database properly: if a file is deleted, its entry is deleted, if it's renamed, its entry is renamed and if it's added, it should be added to the database and to the thumbnail mosaic in the proper place with the default action for the dir (select or deselect). something similar happens when opening the source dir again if there's already a database in place. since the last time, pictures could have been deleted or added.

full view details: by double-clicking a thumbnail or pressing enter with one highlighted, the app would load an overlay on top showing a bigger version, almost full-screen, of the highlighted picture. an X in the top right corner closes this view, same as pressing escape on the keyboard. in this view, below the image we still show the two main action buttons to select or deselect, or maybe just one that toggles the selection state of  the picture, which should be displayed somehow but not necessarily through a frame like in the thumbnail view. pressing left or right in this overlay (but not up or down) moves to the next or previous picture. it could use an animation that is similar to flipping pages of a book or something else that is appropriate. pressing the keyboard shortcuts to select or deselect a picture should also work in this view.

some q&a follows.

what happens if, when moving pictures to the final dir, there is a file with the same name there? the app should prompt if we want to overwrite the picture (in fast mode, same filesystem, the existing one could be unlinked first, then the new pic should be moved in), the second option is adding a suffix to the new pic before the file name extension, and the third option is not to overwrite. the dialogue could have a checkbox to apply the same action to future questions.

what happens if there is a non-regular file (e.g. a directory) with the same name in the destination dir? error dialogue and the process stops there. ideally, we could check this does not happen for any selected picture before starting the move, so the process does not even start.

when are non-selected pictures deleted from the source dir? never in the app. i would do that later manually outside the app, likely deleting the whole source pictures dir and taking down the selection database with it, so the gallery ends up clean.

how should the files in the mosaic be sorted? ideally we could have several options, with the name being the main one, but if the exif data has a date maybe we want to be able to sort by that too? not sure how pictures without exif data should be sorted in that case (name at the end of the list?).

performance and memory use? the app should load almost instantly and most actions, while sometimes having small animation details, should feel snappy and instantaneous. i've never done graphics apps before but i know a bit about opengl or vulkan. i would be worried about what happens if i have a dir with, say, 1000 pictures to select (unlikely to ever reach that number, but let's take it as a baseline). how long does it take to decode and populate the initial view of the thumbnails? if the original pictures are 6000x4000 pixels, maybe we want to blit that after decoding into a much smaller size for the thumbnail and keep it in gpu memory? how many thumbnails like that fit in a few GBs of GPU memory? maybe if we can only show 9 or 12 big thumbnails at the same time, we can keep only those and the previous and next page? and, as we move, decode more pictures to keep the relevant ones in memory? maybe we can decode each picture with a thread to make the initial decode faster? what do we display in the mosaic while the picture has not yet been decoded if we move very fast through it? same for the full view mentioned above. we want to display the picture scaled down or up to almost the display resolution but  that's going to take more memory, so i don't think we can keep 1000 of those without using a lot of system and gpu memory, so you need to do numbers. maybe we can keep only in memory the current full-view picture plus 2 before and 2 after, and re-decode using cpu when needed, trading cpu and memory for that. this is a desktop so battery is not a concern.
